## 6.1 灵矿开采

### 6.1.1 download\_dota8 下载器

DOTA（Dataset for Object Detection in Aerial Images）是经典的遥感目标检测数据集，包含飞机、舰船、车辆、桥梁、运动场等多种航拍目标。但完整 DOTA 数据量较大，现在直接拿它训练并没有必要。因此目前我们使用 Ultralytics 提供的 **DOTA8**。

DOTA8 只有 8 张示例图片，4 张训练、4 张验证。它显然不足以训练出一个真正可用的检测模型，却非常适合我们现在做模型的训练验证，所以我们先写个脚本，把数据下载回来。

创建`ch06` 文件夹，把 `ch05` 文件夹中的内容，全部复制过来。

然后在根目录新建 `download.py`文件，输入：

```python
import os
import zipfile
import urllib.request
from pathlib import Path

def show_progress(block_num, block_size, total_size):
    """
    下载进度显示回调函数。
    urllib 每下载一个数据块，会自动调用一次该函数。
    """

    if total_size <= 0:
        return

    # 已下载大小
    downloaded = block_num * block_size

    # 防止最后一次超过文件总大小
    downloaded = min(downloaded, total_size)

    percent = downloaded / total_size * 100

    print(
        f"\r下载进度: {percent:5.1f}% "
        f"({downloaded / 1024 / 1024:.1f}MB/"
        f"{total_size / 1024 / 1024:.1f}MB)",
        end="")

def download_dota8(dest_dir="dota8"):
    """下载并解压 DOTA8；若已经存在则直接复用。"""

    dest = Path(dest_dir)

    # 已经存在图片时，不重复下载
    if dest.exists() and any(dest.rglob("*.jpg")):
        print(f"数据集已存在: {dest.resolve()}")
        return str(dest.resolve())
   
   #下载文件地址，如果github无法稳定访问，可以选择其他地址
    url = ("https://github.com/ultralytics/assets/releases/download/v0.0.0/dota8.zip")
    zip_path = dest.parent / "dota8.zip"

    try:
        print("正在下载 DOTA8...")
        
        #核心下载函数，reporthook参数用于指定下载过程中的钩子函数，这里是刚刚写的show_progress
        urllib.request.urlretrieve(url, str(zip_path), reporthook=show_progress)

        print("正在解压...")
        with zipfile.ZipFile(str(zip_path), "r") as zf:
            zf.extractall(str(dest.parent))

        os.remove(str(zip_path))
        print(f"数据集准备完成: {dest.resolve()}")
        return str(dest.resolve())

    except Exception as e:
        print(f"下载失败: {e}")
        print("可以手动下载 dota8.zip，并解压到当前项目目录。")
        return None
```

简单解释一下这个下载器代码。

先导入三个标准库：os 处理文件路径，zipfile 解压缩包，urllib.request 下载文件。这都是Python自带的，不需要额外安装。

为了防止下载时间过长，被误认为程序停止运行，所以最好把下载过程信息显示出来。我们是利用`urllib.request.urlretrieve` 方法下载数据，这个方法允许我们指定一个“钩子”函数，每下载一定量的数据就调用一次这个钩子函数。利用这个机制，我们就可以来显示下载过程信息。

代码里的 `show_progress` 函数就是我们自己定义的钩子函数，用来显示下载过程信息。

`download_dota8` 函数开头我们设计了一个**幂等性检查**，所谓幂等性检查就是：如果目标目录已存在且里面有 `.jpg` 文件，就认为数据集已下载，直接返回数据集路径，否则，才会真正开始下载数据。这个设计可以让我们反复运行脚本而不会重复下载数据。这种“小防护”在后面的数据集缓存、模型权重下载、训练断点续跑中都会不断出现。

幂等性检查代码：

```python
if dest.exists() and any(dest.rglob("*.jpg")):
    return str(dest.resolve())
```

真正下载数据的代码：

```python
    try:
        print("正在下载 DOTA8...")
        
        #核心下载函数，reporthook参数用于指定下载过程中的钩子函数，这里是刚刚写的show_progress
        urllib.request.urlretrieve(url, str(zip_path), reporthook=show_progress)

        print("正在解压缩...")
        with zipfile.ZipFile(str(zip_path), "r") as zf:
            zf.extractall(str(dest.parent))

        os.remove(str(zip_path))
        print(f"数据集准备完成: {dest.resolve()}")
        return str(dest.resolve())

    except Exception as e:
        print(f"下载失败: {e}")
        print("可以手动下载 dota8.zip，并解压到当前项目目录。")
        return None

```

这段代码做了三件事：

*   下载：urlretrieve 把远程zip文件拉到本地

*   解压：extractall 将zip内容释放到目标位置

*   清理：删除zip压缩包，只保留解压后的文件

整个过程包裹在 try/except 中。如果网络不通（比如你在没有外网的环境中），它会提示手动下载，而不是直接崩溃。

> 修炼提示：如果你的网络环境无法访问GitHub，可以手动下载 dota8.zip 并解压缩到代码同级目录下。确保目录结构为 dota8/images/train/ 和 dota8/labels/train/ 即可。

## 6.2 灵石炼化：从四角点到旋转框

### 6.2.1 四角点与旋转框

我们在第 1 卷已经见过两种旋转框表示方法：

```text
四角点：
(x1,y1) (x2,y2) (x3,y3) (x4,y4)

旋转框：
(cx, cy, w, h, angle)
```

四角点表示非常直观，也非常符合我们的直觉，因为它直接告诉我们矩形的四个顶点在哪里。很多标注工具默认使用四角点来表示矩形。

而对一个矩形来说，它真正独立的几何信息其实只有 5 个：

*   `cx`：中心点横坐标；
*   `cy`：中心点纵坐标；
*   `w`：一条边长度；
*   `h`：另一条边长度；
*   `angle`：矩形方向。

因此模型内部通常会使用更加紧凑的 `xywhr` 表示矩形。

我们需要做的是：**根据矩形四个顶点，计算出一个规范化的、旋转框形式的 矩形表示。**

“规范化”三个字的核心是**矩形的角度如何确定**。

***

因为原来由 `w` 描述的那条边，现在改成了由 `h` 描述；宽和高交换之后，只要把参考方向同时转过 `90°`，最终描述的仍然是同一个矩形。用更通用的表达就是：

`(cx, cy, w, h, angle)` 与 `(cx, cy, h, w, angle + 90°)`在几何意义上是等价的。

这就带来一个麻烦：**同一个旋转框，可以对应多组完全不同的 `(w,h,angle)` 数值**。

对人来说，这只是不同写法，但对模型训练来说，如果同一个几何目标（标注框）的旋转角度一会儿写成 `30°`，一会儿又写成 `120°`，那么模型面对的训练监督信号就会变得非常混乱。

说明一下：为了统一弧度、角度的表示，后续矩形旋转角度 `angle` 统一使用 `r` 来表示。

由于同一个矩形存在多种等价的“ `xywhr` ”表示，因此必须制定统一的“表达模式”。

### 6.2.3 长边定义法：旋转框表示的统一标准

我们参考Ultralytics的实现标准，采用**长边定义法**。

在介绍**长边定义法**之前，先啰嗦一句 **图像坐标系**。

对于一张数字图像，我们采用如下的图像坐标系：

    o ─────────────────→ +x
    │
    │
    │
    ↓
    +y

原点 `o` 在图像左上角，从左向右为x正方向，从上向下，注意，是从上到下，为y正方向。

这和数学中常见的笛卡尔坐标系有一点区别。

在上述的图像坐标系下，**长边定义法**的规则可以精确写成两条。

###### 规则 1：`w` 表示长边

如果根据四角点得到 `w < h`，就交换宽和高 `w, h  ->  h, w` ，但是只交换两个数字还不行，刚刚说了，角度必须同步调整 `r -> r + π/2` ，也就是 `r -> r + 90°`，这正是上一节动画中看到的情况，两组参数虽然不同，但表示的是完全相同的矩形。

我们统一规定：

> `w` 表示矩形的长边长度，`r` 表示 **长边所在直线** 相对于 `x` 轴正向的顺时针规范化夹角。

注意这里**规范化**夹角的表述，什么叫规范化？上一节我们知道矩形的旋转角度r有多种等价的表述，也就是有多种等价的值（比如30和210），所谓“规范化”，就是我们定一个标准，角度采用同一个范围内的值。

###### 规则 2：把角度统一到固定的 180° 区间

上一个节我们知道，旋转框的角度是一个以180°为周期的量。

所以规范化就是指，我们要把旋转框的角度规定在哪个确定的180度区间内，`[0°, 180°)`? `[-90°, 90°)` 或者 `[-45°, 135°)`?

我们同样参考Ultralytics的实现标准，规定 `r` 处于 `[-45°, 135°)` 区间内，即 `-45° ≤ r < 135°`，如果写成弧度的表示方式，就是：`-π/4 ≤ r < 3π/4` 。

最终，训练标签中的旋转框满足以下两条规则：

*   w ≥ h
*   r ∈ \[-45°, 135°)

其中：

> `w` \*\*表示较长边的长度；
>
> \*\* `r` **表示** `w` **对应边所在直线相对于图像坐标系** `x` **轴正方向顺时针旋转的规范化夹角。**

注意： `r` 有可能取负值，负值的意思就是w边所在的直线相对X轴正方向，逆时针旋转的角度。

### 6.2.4 旋转角度的“跳变”之谜

现在，我们给旋转框规定了一套统一的表示方，问题看起来都已经解决了。不过如果你留意过一些实时显示矩形标注框旋转角度的标注工具，又或者自己开发过标注工具，会发现标准框的旋转角度值会发生跳变。

你是否也因此疑惑过？

###### 1、角度周期边界跳变

假设现在有一个矩形标注框，我们缓慢旋转它，其旋转角度依次为：

```text
130°
132°
134°
134.9°
135°
135.1°
```

由于我们刚刚规定 `r` 的标准取值范围是 `[-45°, 135°)`, 注意这里右端 `135°` 是一个开区间，也就是 `r` 不能真正取到`135°`这个值。因此当旋转角度 `r` 达到 `135°` 时，它的值会跳变成  `-45°` 。这就是**角度周期边界跳变**。这是因为 `r` 的值要符合我们之前的规定而造成的。

请注意： **跳变的是矩形旋转角度的表示，不是矩形本身**。矩形标注框并没有发生跳动，在图像上仍然是连续旋转的。

###### 2、接近正方形时的长短边切换跳变

假设有两个几何形状几乎完全相同的标注框。

第一个框的宽和高分别是：

    w = 100.01
    h = 100.00

因为 `w > h` ，所以 `w` 所对应的边被认为是长边。

而另一个几乎完全相同的框，宽和高分别是：

    w = 99.99
    h = 100.00

这时 `w < h` ，按照长边规范化规则，就需要交换宽和高，`r` 也会随之变化约 `90°`。

从图像上看，这两个矩形的几何形状和姿态可能几乎没有肉眼可见的差异，但是他们记录的旋转角度可能存在 `90°`的差异，比如一个是 `20°` ，另一个是 `110°`。

如果恰好 `w = h`，也就是标注框是正方形。此时不存在唯一的“长边”。正方形旋转 `90°` 后仍然与自身完全重合，因此以哪一条边作为 `w` 的参考边，在几何上都可以成立。

所以，越接近正方形，基于“长边”定义的角度表示就越容易出现约 `90°` 的参数跳变。

再次强调：**这里跳变的是** `xywhr` **中的值，不是标注框突然旋转了** `90°` **。**

说到这里，有个问题顺带提一嘴。

通过前面的介绍，我们很容易发现旋转标注框中的 `r` 和距离、长度这些普通数值很不一样。它有2个明显的特点：

*   周期性：r ≡ r + 180°
*   宽高交换等价性：(w, h, r) 与 (h, w, r + 90°)等价

这会直接带来一个问题。

对于一个目标，假设标注框标注的角度是 `-44.9°`，模型在训练过程中预测的角度是 `134.9°`，如果把它们当作两个普通实数直接相减： `|134.9 - (-44.9)| = 179.8°`，看起来预测错得非常离谱。但考虑到旋转框具有 `180°` 周期：`134.9° ≡ -45.1°`，因此真实的方向差实际上只有：`|-45.1° - (-44.9°)| = 0.2°` ，两个旋转框几乎完全一致，预测是非常准确的。

这也说明 **OBB 的角度不能简单地当成一个普通连续标量来理解**。 如果以后直接使用普通的 MSE 去回归角度，就必须面对周期边界带来的巨大数值误差。所以等真正进入 **OBB Loss** 计算时，我们要专门针对这个问题进行处理。现在先知道有这个问题即可。

### 6.2.5 四角点到 `xywhr`的转换函数

前面几节，我们已经把旋转框最麻烦的几个问题理清楚了：四角点为什么要转换成 xywhr；同一个矩形为什么存在多种等价表示；采用什么规范统一表示一个旋转矩形（标注框）。

现在终于可以把这些规则真正写成转换函数了。

#### 6.2.5.1 创建 `ops.py` 文件

不过，在动手编码之前还有一个现实问题： **这个转换函数的代码应该写在哪里？**

第4卷我们按照“高内聚，低耦合”的原则，根据职责把代码拆分到了不同的文件中，例如： `model.py`文件负责模型解析和模型结构；`dataset.py` 文件负责数据读取与处理；`trainer.py`文件负责训练与验证。

而接下来要写的 `四角点 → xywhr`转换函数，显然不属于模型层，也不属于训练循环。它本质上是一个**几何数据转换操作。** 而且以后我们还会遇到很多类似操作，例如：`xyxy → xywh`、`xywh → xyxy`、`xywhr → 四角点`、`坐标缩放`、`边界裁剪`等等，这些函数都有一个共同特点：**它们负责对数据进行某种通用操作，但本身并不属于某一个具体模型。**

因此，根据“高内聚，低耦合”原则，我们有必要单独建立一个 `ops.py` 文件来存放这些通用操作。

这里的 `ops` 是 `operations` 的缩写，可以简单理解成 **各种通用的数据和几何操作。** 这样以后需要进行旋转框格式转换时，不管是在数据集、模型预测还是可视化代码中，都可以直接调用 `ops.py` 中的各种函数。

在根目录下新建 `ops.py` 文件。

##### 6.2.5.2 CV2：计算机视觉基础库

假设我们已经有了矩形的四个顶点：

```text
(x1, y1)
(x2, y2)
(x3, y3)
(x4, y4)
```

理论上当然可以自己计算：矩形中心在哪里？宽和高分别是多少？矩形旋转了多少度？但是在真正的工程中，**面对一个成熟、常见的问题，如果已经有可靠的成熟实现，就没有必要每次都从零重新造一个。** 四角点到 `xywhr`的转换显然属于这一类问题。

这里我们引入一个重要的库：`cv2` 。

`cv2` 是 **OpenCV** 的 Python 接口。OpenCV 是计算机视觉领域非常常用的基础库，实现了大量成熟的图像与几何处理方法，例如：图像读取与保存、图像缩放、颜色空间转换、边缘检测、轮廓提取、几何变换等等。

再啰嗦两句题外话。写代码的核心能力，并不只是我能不能亲手把这个算法从头写出来，当然这很重要，但是实际开发中还有另一种同样重要的能力：**熟悉有哪些成熟工具可以使用，能不能正确地使用它们。**

可以把这些库和函数理解成我们炼器过程中不断收集的“法器”。每一个函数，都相当于一件已经打造好的“小法器”。学习编程只熟悉基础语法是远远不够的，随着项目越来越复杂，我们还需要不断积累**对常用库、常用函数以及它们能力边界的认识。** 工程能力的一部分，就是不断认识这些"法器"，知道的工具越来越多，以后面对新的问题时，你才会迅速找到合适的工具。当然，并不是要求把常用库的所有 API 全背下来，但至少要知道 “这个库大概能干什么”，以后真正遇到问题时，才知道应该去哪里寻找工具。

回到我们目前要解决的问题上，我们现在要解决的是：给定若干二维点，求一个能够包住这些点的旋转矩形。

CV2这个库正好提供了这样一个函数：cv2.minAreaRect()。它的作用可以非常直白地理解为：**寻找一个能够包围这些二维点，并且面积尽可能小的旋转矩形。**

假设我们已经有了旋转矩形的四个顶点坐标 `pts`，把这四个点交给 `cv2.minAreaRect(pts)`，minAreaRect函数 会计算一个最小面积旋转矩形，并返回如下数据：

    (
        (cx, cy),   # 矩形中心坐标
        (w, h),     # 两条相邻边的长度
        angle       # 与当前 w 所对应边配套的旋转角度

    )

这样我们就很方便的获得了指定矩形的中心、宽高以及旋转角度，而且成熟的视觉库经过长期验证，表现稳定可靠。我们在工程实现上**没有必要把精力花在重复实现一个已经非常成熟的基础几何算法上。**

`minAreaRect()` 方法给了我们指定矩形的中心点坐标、宽和高、旋转角度，那能不能直接把这个结果输出为我们想要的 `xywhr` 呢？

显然还不行，我们之前前面已经为 `xywhr` 制定了统一的规范， `minAreaRect()` 方法返回的结果符合这个规范吗？未必。

所以 `minAreaRect()` 只完成第一步，后续我们要自己把 `minAreaRect()` 的输出结果整理成符合统一规范的表示。

这就是 `xyxyxyxy2xywhr` 函数的实现思路了。

##### 6.2.5.3 实现 `xyxyxyxy2xywhr`

在 `ops.py` 文件中，首先导入两个库：

    import cv2
    import numpy as np

然后输入 `xyxyxyxy2xywhr` 的具体代码：

    def xyxyxyxy2xywhr(corners):
        """
        将旋转框四角点转换为规范化 xywhr。

        支持输入: (8,)、(4, 2)、(N, 8)、(N, 4, 2)等形式

        输出: (N, 5)，每一行为:[cx, cy, w, h, r]

        """

        corners = np.asarray(corners, dtype=np.float32)

        # ---------- 统一输入形状 ----------
        if corners.ndim == 1:
            if corners.size != 8:
                raise ValueError("一维输入必须包含 8 个坐标值")
            corners = corners.reshape(1, 4, 2)

        elif corners.ndim == 2:
            if corners.shape == (4, 2):
                corners = corners.reshape(1, 4, 2)

            elif corners.shape[1] == 8:
                corners = corners.reshape(-1, 4, 2)

            else:
                raise ValueError(
                    "二维输入应为 (4, 2) 或 (N, 8)"
                )

        elif corners.ndim == 3:
            if corners.shape[1:] != (4, 2):
                raise ValueError(
                    "三维输入应为 (N, 4, 2)"
                )

        else:
            raise ValueError("无法识别 corners 的形状")

        rboxes = []

        # ---------- 逐个旋转框处理 ----------
        for pts in corners:

            # 1. 求能够包围四个点的最小面积旋转矩形
            (cx, cy), (w, h), angle_deg = cv2.minAreaRect(
                pts.astype(np.float32)
            )

            # 2. OpenCV 返回角度单位为度，
            #    转换为后续模型使用的弧度
            r = np.deg2rad(angle_deg)

            # 3. 长边规范化：让 w 始终表示较长边
            if w < h:
                w, h = h, w
                r += np.pi / 2

            # 4. OBB 角度以 pi 为周期，
            #    统一到 [-pi/4, 3pi/4)
            while r >= 3 * np.pi / 4:
                r -= np.pi

            while r < -np.pi / 4:
                r += np.pi

            rboxes.append(
                [cx, cy, w, h, r]
            )

        return np.asarray(
            rboxes,
            dtype=np.float32
        ).reshape(-1, 5)

大致分析一下代码，其实理解了 `xyxyxyxy2xywhr` 函数的实现思路，这段代码并不难理解。

###### 1、先把输入整理成统一形状

用户传进来的四角点可能写成：`(x1, y1, x2, y2, x3, y3, x4, y4)`，也可能已经整理成：

```text
[
    [x1, y1],
    [x2, y2],
    [x3, y3],
    [x4, y4]
]
```

甚至一次传入多个旋转框，所以函数首先需要**把各种允许的输入统一整理成** `(N, 4, 2) `**的形式**，最终保证每一个 `pts` 都是 `4 × 2` 形状的四个顶点。

这也是工程代码中非常常见的一步： **先统一数据格式，再进行真正的计算。**

###### 2、使用 CV2 求旋转矩形

真正完成几何计算的核心只有这一段代码：

```python
(cx, cy), (w, h), angle_deg = cv2.minAreaRect(
    pts.astype(np.float32)
)
```

输入 4 个二维坐标点，输出中心位置+两条边长度+旋转角度，这里把输入转换成 `np.float32` ，是为了使用 CV2 要求的数值格式进行计算。

注意，我们把 `minAreaRect` 返回的角度命名为 `angle_deg`，而不是直接叫 `r`，是因为 **它现在还只是 OpenCV 返回的原始角度，并不是我们最终规范化后的** `r` **。**

###### 3、角度从“度”转换成“弧度”

`minAreaRect` 返回的 `angle_deg` 使用的是“度”，但是神经网络中的角度计算通常使用弧度，所以我们做一个转换：

```python
r = np.deg2rad(angle_deg)
```

把 “角度” 转换为“弧度”。例如：`180° → π，90°  → π / 2，45°  → π / 4`。

###### 4、执行长边规范化

现在虽然已经有 `w`、`h`、`r`，但 `minAreaRect` 函数返回的 `w` 不一定就是我们前面规定的长边。因此检查：

```python
if w < h:
```

如果成立，就交换长短边，并处理角度：

```python
w, h = h, w
r += np.pi / 2
```

这样才能保证 `w ≥ h` ，同时 `r` 仍然与当前 `w` 所对应的边匹配。

###### 5、规范角度范围

即使已经完成长边交换，`r`仍然可能超出我们规定的 `[-π/4, 3π/4)`的范围，所以最后利用 `r ≡ r + π` 这一性质进行调整。

如果`r`太大，则减去一个周期：

```python
while r >= 3 * np.pi / 4:
    r -= np.pi
```

如果`r`太小。加上一个周期：

    while r < -np.pi / 4:
        r += np.pi

这样操作以后，就能确保`r`最终一定落到 `[-π/4, 3π/4)`区间内。

代码写到这里，尤其是我们写了这么多数值处理的代码，也许有人会想： `minAreaRect()` 到底把哪条边叫 `w`？它原始返回的角度范围究竟是多少？由于不同版本的CV2库的具体实现不同，所以不同版本之间有差异，限于篇幅我们这里不做详细的介绍，有兴趣的可以自行找相关资料了解。

到这里，前面几节讲过的所有规则终于真正落到了代码中。

### 6.2.6 反向转换：`xywhr → xyxyxyxy`

刚刚的 `xyxyxyxy2xywhr()` 函数把数据集中的四角点转换成模型更容易处理的 `xywhr`。但到了“标签检查”和“预测结果可视化”阶段，我们需要把旋转框真正画到图片上， Matplotlib、OpenCV 等绘图库最终还是需要知道矩形四个顶点的位置。

所以还需要写一个反向转换函数 `xywhr2xyxyxyxy`，继续在 `ops.py` 中加入：

```python
def xywhr2xyxyxyxy(rboxes):
    """
    将 xywhr 转换为四角点。
    输入:(5,) 或 (N, 5)，每一行为 [cx, cy, w, h, r]
    输出:(N, 4, 2)
    """
    
    rboxes = np.asarray(rboxes, dtype=np.float32)

    if rboxes.ndim == 1:
        rboxes = rboxes.reshape(1, -1)

    if rboxes.ndim != 2 or rboxes.shape[1] != 5:
        raise ValueError("rboxes 的形状应为 (5,) 或 (N, 5)")

    cx = rboxes[:, 0]
    cy = rboxes[:, 1]
    half_w = rboxes[:, 2] / 2
    half_h = rboxes[:, 3] / 2
    r = rboxes[:, 4]

    cos_r = np.cos(r)
    sin_r = np.sin(r)

    dx = np.array([-1, 1, 1, -1], dtype=np.float32)
    dy = np.array([-1, -1, 1, 1], dtype=np.float32)

    corners = np.zeros((len(rboxes), 4, 2), dtype=np.float32)

    for i in range(4):
        corners[:, i, 0] = cx + dx[i] * half_w * cos_r - dy[i] * half_h * sin_r
        corners[:, i, 1] = cy + dx[i] * half_w * sin_r + dy[i] * half_h * cos_r

    return corners
```

这段代码中的三角函数看起来有一点吓人，但真正的思路并不复杂。

对于一个没有旋转、中心位于原点、宽高分别是 `w` 和 `h` 的矩形，它的四个角点分别是：

```text
(-w/2, -h/2)
( w/2, -h/2)
( w/2,  h/2)
(-w/2,  h/2)
```

也就是代码中的 `dx` 、`dy` 分别乘上 `w/2` 和 `h/2`。

接下来，把每个角点绕中心旋转 `r`。二维旋转使用的公式就是：`x' = x cos(r) - y sin(r)`，`y' = x sin(r) + y cos(r)`。

最后再做个平移操作，把旋转后的局部坐标加上中心位置 `(cx, cy)`，就得到了四个角点在整张图像中的真实坐标。
