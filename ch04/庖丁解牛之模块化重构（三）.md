# 模块化重构（三）



## 4.3 合炉验器：重构后的验证

前面已经完成了 `main.py` 的模块化重构。现在只需要确认一件事：**重构以后，模型和训练流程还能不能正常运行，输出结果是不是正确。**

---

### 4.3.1 运行完整工程

打开终端，进入 `ch04/` 目录：

运行：

```bash
python main.py
```

注意要在 `ch04/` 目录下执行，这样 Python 才能正确找到：

```text
model.py
dataset.py
trainer.py
nn/
```

程序开始训练前，会先检查 P3、P4、P5 三个尺度的输出。

正常情况下应看到：

```text
各尺度输出形状:
  P3: [1, 10, 32, 32]  (stride=8)
  P4: [1, 10, 16, 16]  (stride=16)
  P5: [1, 10, 8, 8]    (stride=32)
```

这里主要检查三点：

- P3、P4、P5 的尺寸是否分别为 `32×32`、`16×16`、`8×8`；
- stride 是否分别为 8、16、32；
- 输出通道数是否为 10，即 `2 个类别 + 8 个框属性`。

如果这些结果和第 3 卷一致，说明模型结构在拆分过程中没有被破坏。

---

### 4.3.2 检查训练链路

尺寸检查通过后，程序会正式进入训练。

训练过程中，`tqdm` 会显示当前 epoch 的进度和 batch Loss，例如：

```text
Epoch 1/20:  60%|██████████████▍         | 12/20 [00:01<00:00, loss=30.1245]
```

每个 epoch 结束后，会输出：

```text
Epoch [ 1/20] | Train Loss: 30.2341 | Val Loss: 30.1842
  --> 保存当前最佳模型，Val Loss = 30.1842
```

这里主要检查：

1. `tqdm` 进度条是否正常；
2. Train Loss 是否能够正常计算；
3. Val Loss 是否能够正常计算；
4. 训练能否连续完成多个 epoch。

这里使用的是随机生成的虚拟数据，因此每次运行的 Loss 数值可能不同，不需要关注某一个固定结果。

---

## 4.3.3 检查权重文件

训练开始后，`runs/weights/` 目录中应该生成：

```text
weights/
├── last.pt
└── best.pt
```

其中：

- `last.pt`：保存最近一次训练结果；
- `best.pt`：验证集 Loss 更小时更新。

如果模型能够正常完成前向传播、反向传播、验证并保存权重，就说明重构后的完整训练链路已经跑通。

---

### 4.3.4 常见错误检查

#### `ModuleNotFoundError: No module named 'nn'`

确认当前工作目录是 `ch04/` ，并确认存在：

```text
ch04/nn/__init__.py
```

#### `ImportError: cannot import name 'Conv' from 'nn'`

检查 `nn/__init__.py` 中是否正确导出：

```python
from .conv import Conv, autopad
```

同时检查 `block.py` 中是否正确导入：

```python
from .conv import Conv
```

#### P3、P4、P5 输出尺寸不正确

重点检查 `model.py` 中：

- Backbone 的下采样次数；
- P3、P4、P5 的保存位置；
- FPN 的上采样和 `Concat`；
- 三个 Head 的输入通道数。

## 4.4 名门规制：对标 Ultralytics 目录规范

到这里，我们已经亲手完成了模块拆分，并确认重构后的模型能够正常运行。

现在再回头看看 Ultralytics 的源码结构，就容易理解得多了。这里只列出与我们当前代码相关的部分：

```text
ultralytics/
├── nn/
│   ├── modules/
│   │   ├── __init__.py
│   │   ├── conv.py         ← Conv, autopad, ...
│   │   ├── block.py        ← Bottleneck, C2f, C3k2, SPPF, ...
│   │   ├── head.py         ← Detect, OBB, ...
│   │   └── transformer.py  ← ...
│   └── tasks.py            ← DetectionModel（模型主体）
├── data/
│   ├── dataset.py          ← YOLODataset
│   ├── base.py             ← BaseDataset
│   └── build.py            ← build_dataloader
├── engine/
│   ├── trainer.py          ← BaseTrainer
│   └── validator.py        ← BaseValidator
├── models/
│   └── yolo/
│       ├── model.py        ← YOLO 门面类
│       └── obb/
│           ├── train.py    ← OBBTrainer
│           └── predict.py  ← OBBPredictor
└── utils/
    ├── ops.py              ← 各种工具函数
    └── metrics.py          ← mAP 计算
```

我们当前的目录结构是：

```text
ch04/
├── nn/
│   ├── __init__.py
│   ├── conv.py
│   └── block.py
├── model.py
├── dataset.py
├── trainer.py
└── main.py
```

两者大致的对应关系如下：

| 我们的文件 | Ultralytics 对应位置 | 说明 |
| --- | --- | --- |
| `nn/conv.py` | `ultralytics/nn/modules/conv.py` | 暂时只有 `Conv`、`autopad` |
| `nn/block.py` | `ultralytics/nn/modules/block.py` | 暂时只有 `Bottleneck`、`C2f`、`C3k2`、`SPPF` |
| `nn/__init__.py` | `ultralytics/nn/modules/__init__.py` | 统一导出已经实现的算子 |
| `model.py` | `ultralytics/nn/tasks.py` | 暂时硬编码模型结构 |
| `dataset.py` | `ultralytics/data/dataset.py` + `build.py` | 暂时使用虚拟数据 |
| `trainer.py` | `ultralytics/engine/trainer.py` | 暂时只有基础训练、验证和保存 |
| `main.py` | 项目入口 | 负责创建和组装各模块 |

可以看到，我们现在的工程虽然很小，但已经开始具备 Ultralytics 的基本分层思路。

模块化之后，各部分职责更加清楚：

```text
nn/          → 网络算子
model.py     → 模型结构
dataset.py   → 数据加载
trainer.py   → 训练流程
main.py      → 组装入口
```

这样做的直接好处是：

- 修改网络算子时，主要改 `nn/`；
- 修改模型结构时，主要改 `model.py`；
- 更换数据集时，主要改 `dataset.py`；
- 增加 AMP、EMA、学习率调度等功能时，主要改 `trainer.py`。

不同功能彼此分开，后续升级时不需要反复修改一个越来越大的 `main.py`。这就是模块化重构真正带来的价值：

> **每个模块各司其职，又能够通过清晰的接口重新组合成一个完整工程。**

# 本卷小结

这一卷完成了从单文件代码到模块化工程的第一次重构。我们把网络算子、模型结构、数据加载和训练流程分别拆到独立模块中，并通过完整运行确认重构前后的功能保持一致。到这里，代码的组织方式已经开始接近真正的 YOLO 工程。

这一卷涉及的几个核心设计原则也已经逐渐清楚：

- **高内聚**：每个文件集中完成自己的职责；
- **低耦合**：模块之间通过明确的接口通信；
- **统一导出**：`nn/__init__.py` 对外提供统一入口；
- **入口简化**：`main.py` 只负责创建和组装；

到这里，第 4 卷完成的是**代码组织层面的模块化**。

但还有一个问题没有解决：`model.py` 中的网络结构仍然是硬编码的。通道数、层数、模块类型都直接写在 Python 代码里。

下一卷，我们尝试把网络结构从 Python 中抽离出来，写进 YAML 配置文件，实现 `parse_model` 动态读取配置并构建模型。
